  - 同步更新根 README CI/CD 表与 `deploy/README.md`（表 + 手动构建用法小节 + GHCR 标签说明）。

### 追加：手动构建首次运行失败排查（2026-08-25 晚）
- 现象：Manual Build #1 在 `Build artifacts (backend + frontend)` 步骤报错 `Can't find action.yml under .github/actions/build`。
- 根因：仓库 `.gitignore` 原有 `**/build` 规则，把本地创建的 composite action 目录 `.github/actions/build/` 整体忽略，导致该目录未被 commit/push，GitHub Actions runner 找不到 `action.yml`。
- 修复：在 `.gitignore` 末尾追加例外规则：
  ```
  !.github/actions/build/
  !.github/actions/build/**
  ```
  验证：`git status --short .github/actions/` 显示 `?? .github/actions/`（已解除忽略），`git add --dry-run` 可正常加入索引。
- 待用户操作：执行 `git add .github/actions/build/ .gitignore && git commit ... && git push` 后重新触发 Manual Build。

### 追加：docs.yml 生成 CHANGELOG 失败排查（2026-08-25 晚）
- 现象：Docs 工作流 #2 在 `Update CHANGELOG on main` 步骤失败，`git-cliff` 报错 `Filter "trim_start_matches" was called on an incorrect value: got 'null' but expected a String`。
- 根因：`cliff.toml` 模板里 `{{ version | trim_start_matches(pat="v") }}` 在 `docs.yml` 未传 `--tag` 时被调用，此时最新未发版区块的 `version` 为 `null`。
- 修复：在 `cliff.toml` 给 `version` 加 `default(value="Unreleased")` 兜底：`{{ version | default(value="Unreleased") | trim_start_matches(pat="v") }}`。
- 验证：`cliff.toml` TOML 语法校验通过。

### 追加：docs.yml 生成 CHANGELOG 失败排查 2（2026-08-25 晚）
- 现象：推送上一个 `cliff.toml` 修复后，Docs #3 仍在 `Update CHANGELOG on main` 失败，新报错 `Filter "date" received an incorrect type for arg 'value': got 'Null' but expected i64|u64|String`。
- 根因：同一个未发版区块，`timestamp` 也是 `null`，`timestamp | date(format="%Y-%m-%d")` 无法渲染。
- 修复：把模板改成条件渲染日期：
  ```
  ## [{{ version | default(value="Unreleased") | trim_start_matches(pat="v") }}]{% if timestamp %} - {{ timestamp | date(format="%Y-%m-%d") }}{% endif %}
  ```
  有 tag 时正常显示日期；无 tag 的未发版区块显示为 `## [Unreleased]`（不带日期，避免 null 崩溃）。
- 验证：`cliff.toml` TOML 语法校验通过。
- 待用户操作：提交推送 `cliff.toml` 修改，docs.yml 会在下次 push 到 main 时自动重跑。

### 追加：ci.yml kubectl dry-run 失败排查（2026-08-25 晚）

### 追加：release.yml 镜像构建失败排查（2026-08-25 晚）
- 现象：推送 tag `4.2.0` 触发 release.yml，`images` job 全部后端镜像报错 `lstat /build/libs: no such file or directory`；前端镜像也失败。
- 根因：`release.yml`/`manual-build.yml` 的 `images` job 用 `actions/download-artifact@v4 path: .` 下载制品，但 artifact 路径还原后与 Dockerfile 期望的 `build/libs/` 不一致（可能被 upload-artifact v4 的 glob 路径处理剥离了前缀），导致 Docker 上下文里找不到 jar。
- 修复：在制品下载后增加显式 stage step：
  - 后端：用 `find . -name '<name>-boot-*-ga.jar'` 定位 jar，复制到 `${{ matrix.context }}/build/libs/`。
  - 前端：用 `find . -type d -path '*/maxkey-web-app/dist'` 定位 dist，复制到 `deploy/docker/{frontend,mgt-frontend}/dist`。
  - 同时修复了 `manual-build.yml` 的 `smoke-test` job（它也下载制品做本地构建）。
- 验证：5 个 workflow YAML 全部通过 PyYAML 语法校验。
- 待用户操作：提交推送 `release.yml`、`manual-build.yml`；然后删除并重新推送 tag `4.2.0` 触发完整 release 重跑。

### 追加：release.yml deploy-test mysql rollout 超时（2026-08-25 晚）
- 现象：Release #3 的 5 个镜像全部构建成功，但 `deploy-test` job 在 `Wait for rollout` 步骤失败，`mysql` Deployment 超时 `0 of 1 updated replicas are available`。
- 根因分析：
  1. MySQL 镜像 `mysql:8.4.2` 来自 Docker Hub，GitHub Actions runner 可能因网络/限流导致拉取慢或失败。
  2. MySQL 容器 `limits.memory: 1Gi` 对 MySQL 8.4 初始化 11MB SQL 偏紧，容易 OOM。
  3. 后端 Dockerfile 里有 `CMD sleep 60; java ...`，会拖慢 K8s rollout 且与 livenessProbe 配合差。
  4. 后端 `Xmx2048m` 与容器 `memory: 2Gi` 边距不足，在 kind 单节点里容易 OOM。
  5. `release.yml` 失败时没有 Pod describe/logs，不便于诊断。
- 修复：
  - `deploy/k8s/base/mysql/mysql-deployment.yaml`：增大资源（limits 2Gi/2CPU），`imagePullPolicy: IfNotPresent`，加 `startupProbe`/`readinessProbe`/`livenessProbe` 用 `mysqladmin ping`，追加 `--explicit-defaults-for-timestamp=1` 与 `--default-authentication-plugin=mysql_native_password`。
  - `maxkey-webs/maxkey-web-{maxkey,mgt,openapi}/Dockerfile`：删除 `sleep 60`，JVM `Xmx` 从 2048m 降到 1536m。
  - `deploy/k8s/base/maxkey{,-mgt,-openapi}/deployment.yaml`：加 `startupProbe`，调整 `readinessProbe`/`livenessProbe` 参数。
  - `.github/workflows/release.yml`：kind 创建后预加载 `mysql:8.4.2` 与 `nginx:stable` 到 kind 节点；`rollout status` timeout 从 420s 提到 600s；失败时自动打印 `get pods`/`describe`/`logs`/`events`。
- 验证：全部 workflow 与 deploy YAML 通过 PyYAML 语法校验。
- 待用户操作：提交推送上述修改，删除并重新推送 tag `4.2.0` 触发完整 release 重跑。
