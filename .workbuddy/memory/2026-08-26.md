## MaxKey Release 未创建 + deploy-test mysql 失败根因定位

用户反馈：tag `4.2.0` 存在，但 GitHub Releases 没有 4.2.0；Actions 存在异常（deploy-test mysql rollout 超时、CI dry-run 旧失败截图）。

### 分析结论

1. **Release 未创建是结果，不是原因**：`release.yml` 的 `release` job 依赖 `deploy-test`，`deploy-test` 失败导致 `release` 被跳过，因此没有 GitHub Release。
2. **mysql rollout 超时的真实根因**：`deploy/k8s/base/mysql/mysql-deployment.yaml` 中使用了 MySQL 8.4 已删除的变量 `--default-authentication-plugin=mysql_native_password`，导致 MySQL 容器启动即崩溃，探针永远失败。
3. **CI dry-run 截图是旧运行**：本地 `ci.yml` 已改为 `kustomize build ... | kubectl apply --dry-run=client --validate=false -f -`，不再依赖 K8s 集群。
4. **GHCR 包私有风险**：即使仓库公开，GHCR 包默认私有，kind 拉取后端镜像时可能 `ImagePullBackOff`。

### 修复内容

- `deploy/k8s/base/mysql/mysql-deployment.yaml`
  - 删除 `--default-authentication-plugin=mysql_native_password`。
  - 改为 `--authentication-policy=*,caching_sha2_password`（MySQL 8.4 合法语法）。
- `deploy/docker/mysql/conf.d/mysqld.cnf`
  - 删除 `slow_query_log=on;` 末尾分号，避免配置值变成 `on;`。

## MaxKey CI dry-run 与 K8s deploy-test 第二轮修复

用户反馈：CI `build-and-smoke` 仍失败；`故障.txt` 中 MySQL startup probe 失败、MaxKey 连接 MySQL 被拒绝、部署的 MaxKey 镜像仍为 `latest`。

### 分析结论

1. **CI dry-run 仍尝试连接 localhost:8080**：`kubectl apply --dry-run=client --validate=false` 仍会触发 API discovery，无 kubeconfig 时连接默认 `localhost:8080` 被拒绝。
2. **MySQL probe 失败根因**：`mysqld.cnf` 只在 `[mysqld]` 段配置 `socket=/var/lib/mysql/mysql.sock`，`[client]` 段未配置；`mysqladmin` 作为客户端读取默认 socket 路径（`/var/run/mysqld/mysqld.sock`），找不到服务器而探针失败。
3. **`Can't find error-message file` 根因**：MySQL 8.4 Docker 镜像编译默认路径为 `/usr/share/mysql-8.4/english`，但实际文件位于 `/usr/share/mysql/english`，需显式设置 `lc-messages-dir`。
4. **镜像仍为 `latest` 根因**：`base/kustomization.yaml` 中固定了 `newTag: latest`，overlay 的 tag 设置被 base 覆盖。

### 修复内容

- `.github/workflows/ci.yml`
  - CI 的 K8s 校验改为完全离线的 `kustomize build` 检查，不再调用 `kubectl`。
- `deploy/docker/mysql/conf.d/mysqld.cnf`
  - `[client]` 段增加 `socket=/var/lib/mysql/mysql.sock`，与 `[mysqld]` 保持一致。
  - `[mysqld]` 段增加 `lc-messages-dir=/usr/share/mysql/english`，消除 errmsg.sys 找不到错误。
- `deploy/k8s/base/kustomization.yaml`
  - `images` 中只保留 `newName`，去掉 `newTag: latest`，避免覆盖 overlay/CI 的标签。
- `deploy/k8s/overlays/dev/kustomization.yaml`
  - `newTag` 改为 `latest`（便于手动测试），CI 通过 `kustomize edit set image` 覆盖为实际版本。
- `deploy/docker/docker-compose.yml`
  - MySQL `command` 与 K8s 保持一致，追加 `--explicit-defaults-for-timestamp=1` 和 `--authentication-policy=*,caching_sha2_password`。
- `.github/workflows/release.yml`
  - `deploy-test` 增加创建 GHCR imagePullSecret 并绑定 default serviceaccount，防止 kind 拉取私有 GHCR 镜像失败。
  - `Debug on rollout failure` 增加 MySQL 配置 dump、init 目录列表，便于下次失败精确定位。
  - 去掉 debug step 中 `kubectl exec` 的 `-t` 参数（CI 无 TTY）。
- `deploy/README.md`
  - 保留「说明 / 配置 / 部署 / 访问测试」四段式结构。
  - 新增「五、常见问题排查」：Release 未创建原因、mysql rollout 超时排查、GHCR 私有包处理、CI dry-run 旧问题说明。
  - 补充 MySQL 8.4 认证插件说明、imagePullSecret 命令、kind 验证步骤。

### 追加修复（MySQL 真正根因：K8s 覆盖 command 导致跳过 entrypoint）

用户贴出完整日志后重新分析：

- **K8s 错误日志**：`Fatal error: Please read "Security" section of the manual to find out how to run mysqld as root!` + `Newly created data directory /var/lib/mysql is unusable`。
- **根因**：K8s 的 `command: [mysqld, ...]` 覆盖了 MySQL 官方镜像的 `docker-entrypoint.sh` entrypoint，导致：没有创建 `mysql` 用户、没有初始化数据目录、没有执行 init SQL、还以 root 身份直接跑 mysqld 崩溃。
- **之前改的 `--default-authentication-plugin` 不是唯一问题**，即使删掉该参数，`command` 覆盖 entrypoint 仍会让 MySQL 起不来。

### 修复内容

- `deploy/k8s/base/mysql/mysql-deployment.yaml`
  - 删除 `command` 字段，改用官方镜像默认 entrypoint。
  - 扩大资源：requests 2Gi/1CPU，limits 4Gi/2CPU（用户要求资源不足时扩大）。
- `deploy/docker/docker-compose.yml`
  - 删除 MySQL `command`，同样保留 entrypoint。
  - healthcheck `retries` 20→60，`start_period` 60s→120s，给 11MB SQL 初始化更长时间。
- `deploy/docker/mysql/conf.d/mysqld.cnf`
  - `character-set-server=utf8` → `utf8mb4`。
  - 追加 `collation-server=utf8mb4_unicode_ci` 与 `explicit-defaults-for-timestamp=1`。
  - `[mysql]` / `[client]` 默认字符集改为 `utf8mb4`。
- `deploy/README.md`
  - 2.4 节补充“K8s 不覆盖 command”说明与资源配置说明。
  - 5.2 节 troubleshooting 把“覆盖 command”列为首要原因。
