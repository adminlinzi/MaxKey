# 2026-08-26

## MaxKey Release 未创建 + deploy-test mysql 失败根因定位

用户反馈：tag `4.2.0` 存在，但 GitHub Releases 没有 4.2.0；Actions 存在异常（deploy-test mysql rollout 超时、CI dry-run 旧失败截图）。

### 分析结论

1. **Release 未创建是结果，不是原因**：`release.yml` 的 `release` job 依赖 `deploy-test`，`deploy-test` 失败导致 `release` 被跳过，因此没有 GitHub Release。
2. **mysql rollout 超时的真实根因**：`deploy/k8s/base/mysql/mysql-deployment.yaml` 中使用了 MySQL 8.4 已删除的变量 `--default-authentication-plugin=mysql_native_password`，导致 MySQL 容器启动即崩溃，探针永远失败。
3. **CI dry-run 截图是旧运行**：本地 `ci.yml` 已改为 `kustomize build ... | kubectl apply --dry-run=client --validate=false -f -`，不再依赖 K8s 集群。
4. **GHCR 包私有风险**：即使仓库公开，GHCR 包默认私有，kind 拉取后端镜像时可能 `ImagePullBackOff`。

### 修复内容

- `deploy/k8s/base/mysql/mysql-deployment.yaml`
  - 删除 `--default-authentication-plugin=mysql_native_password`。
  - 改为 `--authentication-policy=*,caching_sha2_password`（MySQL 8.4 合法语法）。
- `deploy/docker/mysql/conf.d/mysqld.cnf`
  - 删除 `slow_query_log=on;` 末尾分号，避免配置值变成 `on;`。
- `deploy/docker/docker-compose.yml`
  - MySQL `command` 与 K8s 保持一致，追加 `--explicit-defaults-for-timestamp=1` 和 `--authentication-policy=*,caching_sha2_password`。
- `.github/workflows/release.yml`
  - `deploy-test` 增加创建 GHCR imagePullSecret 并绑定 default serviceaccount，防止 kind 拉取私有 GHCR 镜像失败。
  - `Debug on rollout failure` 增加 MySQL 配置 dump、init 目录列表，便于下次失败精确定位。
  - 去掉 debug step 中 `kubectl exec` 的 `-t` 参数（CI 无 TTY）。
- `deploy/README.md`
  - 保留「说明 / 配置 / 部署 / 访问测试」四段式结构。
  - 新增「五、常见问题排查」：Release 未创建原因、mysql rollout 超时排查、GHCR 私有包处理、CI dry-run 旧问题说明。
  - 补充 MySQL 8.4 认证插件说明、imagePullSecret 命令、kind 验证步骤。

### 验证

全部 workflow 与 deploy YAML 通过 PyYAML 语法校验；`cliff.toml` 通过 TOML 校验。

### 追加修复（deploy-test namespace 缺失）

- `.github/workflows/release.yml`
  - 原因：`Create GHCR image pull secret for kind` 在 `kubectl -n maxkey create secret` 时，`maxkey` namespace 尚未创建（kustomize apply 在后面），导致报错 `namespaces "maxkey" not found`。
  - 修复：在创建 secret 前先 `kubectl create namespace maxkey --dry-run=client -o yaml | kubectl apply -f -`；secret 本身也改为 dry-run 生成 YAML 后 apply，避免重复创建报错。
